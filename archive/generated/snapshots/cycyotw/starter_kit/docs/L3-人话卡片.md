# L3 混合编译器 · 人话卡片

> 这份文档的目标：**没有编译原理背景的人也能读懂每一个模块在干什么。**
> 每张卡片回答同样三个问题——它干什么、为什么这么设计、换个输入会怎样。
>
> **如果读到某张卡片时冒出的疑问是「可是为什么非得有这一步？」**，
> 说明你要的是更前面那一层——请先读 [`L3-零基础前传.md`](L3-零基础前传.md)：
> 处理器为什么读不懂文字、寄存器是什么、为什么没有 if。
> 那一层是所有技术文档默认省略的东西，我们把它单独写了出来。

---

## 它整体在解决什么问题

Hybrid-QASM 是一份**混着两种东西**的程序：

```text
OPENQASM 2.0;
include "qelib1.inc";
qreg q[2];
creg c[2];
h q[0];                        <- 量子部分
measure q[0] -> c[0];          <- 量子部分（测量，把量子结果变成 0 或 1）
classical {                    <- 经典部分
  if (c[0] == 1) { r1 = 100; } else { r1 = 10; }
  r1 = r1 + 5;
}
cx q[0], q[1];                 <- 量子部分
```

量子部分要交给量子芯片，经典部分要交给普通处理器。两种硬件、两套指令，
必须先把它们拆开，各自翻译成对应硬件听得懂的话。

`compile_hybrid()` 就做这件事，输出两样东西：

1. **量子操作序列** —— `["h q[0];", "measure q[0] -> c[0];", "cx q[0], q[1];"]`
2. **RISC-V 汇编** —— 经典部分翻译成处理器指令

```text
源码 ──拆分──> 经典块文本 ──分词──> 词 ──语法分析──> 语法树 ──代码生成──> 汇编
     └────────> 量子语句（保持原顺序）
```

四个步骤，四个文件，一步只干一件事。这样拆的好处是：出错时能立刻定位到是哪一层错了，
答辩时也能一层一层讲清楚。

## 卡片 1 · `loomq/hybrid.py` —— 拆分与总装

**干什么**
把源码切成"量子部分"和"经典块"两摞，然后调度后面三个模块，最后把结果拼起来。

**为什么这么设计**
拆分要自己一个字符一个字符地扫，不能用正则表达式。因为 `classical { ... }`
里面还会套花括号（`if/else` 的语句块），正则匹配不了这种嵌套；
而且注释里、字符串里出现的花括号不能算数，扫描时要跳过它们。

量子语句**原样保留**（只把多余空白压成一个空格），不做任何重写。
理由是评测方是拿同一份源码推导参考答案的，保持原样最不容易对不上。

**换个输入会怎样**
- 经典块可以出现在任何位置，也可以出现**多个**——多个块的效果是接在一起的，
  第一个块里给 `r1` 赋的值，第二个块里读得到。
- 没有经典块 → 汇编是一条空操作，量子部分照常输出。
- 花括号没闭合 → 报错并指出是 `classical` 块的问题，不会默默给出错误结果。

## 卡片 2 · `loomq/hybrid_lexer.py` —— 分词

**干什么**
把文本切成一个个"词"。

```text
"r1 = r1 + 5;"  ->  [r1] [=] [r1] [+] [5] [;]
```

**为什么这么设计**
后面的语法分析只想关心"词和词的关系"，不想再操心空格、换行、注释这些排版问题。
分词器把这些噪音一次性清干净，后面就清爽了。

**换个输入会怎样**
- 缩进、换行、空格随便写，结果完全一样。
- `//`、`#` 行注释和 `/* */` 块注释都会被丢掉。
- 出现文法里没有的字符（比如 `*`）→ 报错，并指出**第几行第几列**。

## 卡片 3 · `loomq/hybrid_parser.py` —— 语法分析

**干什么**
把一串平铺的词，组装成一棵有层次的"语法树"。

```text
r1 = r1 + 5;
->  Assign(target=1, expr=BinOp(op='+', left=Reg(index=1), right=Num(value=5)))
```

**为什么这么设计**
文本是平的，但语义是有层次的。`if` 里面套 `if`、`a + b - c` 谁先算，
这些关系只有变成树才说得清楚。树建好之后，"翻译成汇编"和"直接算出答案"
就都只是遍历这棵树而已。

用的是**递归下降**写法：文法里每一条规则对应一个函数，规则套规则就是函数调函数。
好处是**嵌套的 if/else 天然就支持了**——不需要为"套了几层"写任何特殊处理。
赛题公开样例是平的，但正式评测明写会有"不同分支结构"，所以一开始就按能嵌套来写。

**换个输入会怎样**
- `else if` 链、任意层嵌套 → 直接支持。
- 只有一条语句时不写花括号、句尾漏个分号 → 也能读懂（只放宽、不收紧）。
- 写了 `r0` 或 `r10` → 报错，因为赛题规定经典寄存器只有 `r1..r9`。

## 卡片 4 · `loomq/hybrid_codegen.py` —— 代码生成

**干什么**
把语法树翻译成 RISC-V 汇编文本，能直接丢进官方 `riscv_emulator.py` 执行。

**为什么这么设计**
官方模拟器只给了 **7 条指令**（`li add sub addi beq bne j`），整个翻译就是在这 7 条里凑。

寄存器怎么分：

| 用途 | 寄存器 | 谁定的 |
|---|---|---|
| 经典变量 `r1..r9` | `x1..x9` | 赛题规定 |
| 测量位 `c[k]` | `x10, x11, ...` | 赛题规定，由评测系统注入 |
| 中间结果 | `x20` 往上 | 我们自己定 |

**这里有两个很容易踩的坑，也是这个模块大部分设计的由来：**

1. **`beq / bne` 只能比较两个寄存器，不能拿寄存器跟常数比。**
   所以 `if (c[0] == 1)` 必须先把常数 `1` 装进一个临时寄存器，才能比较。

2. **临时寄存器必须避开 `x10` 起的测量位。**
   如果中间结果写进了 `x10`，就会把评测系统注入的测量结果**覆盖掉**，
   而且这种错误只在特定测量值下才暴露，很难发现。
   我们从 `x20` 起用，并且会随测量位数量继续往上让。
   算完还会把用过的临时寄存器**清零**——因为官方模拟器返回的是"所有非零寄存器"，
   留下的中间结果会混进最终状态里，跟参考答案对不上。

`if / else` 翻译成什么样：

```text
if (条件) { A } else { B }

    <算出条件两边的值>
    b<条件的反面>  左, 右, L_ELSE_1     # 条件不成立就跳去 else
    <A 的指令>
    j L_END_1
L_ELSE_1:
    <B 的指令>
L_END_1:
```

注意分支用的是**条件的反面**：`==` 用 `bne` 跳走，`!=` 用 `beq` 跳走。
因为汇编里的分支表达的是"什么时候**绕开**这段代码"。

**换个输入会怎样**
生成的汇编自带注释和语句编号，人可以直接读。上面那个例子编译出来是：

```asm
# --- 第 1 条语句 ---
    li x20, 1                # 常数 1
    bne x10, x20, L_ELSE_1   # 两边不相等就跳走
    li x1, 100               # r1 = 100
    j L_END_1                # then 分支执行完，跳过 else
L_ELSE_1:
    li x1, 10                # r1 = 10
L_END_1:
# --- 第 2 条语句 ---
    addi x20, x1, 5          # + 5
    add x1, x20, x0          # r1 = 上面算出来的值
# --- 清理临时寄存器，只留下 r1..r9 与测量位 ---
    li x20, 0
```

## 卡片 5 · `loomq/hybrid_interp.py` —— 参考解释器

**干什么**
不生成任何汇编，直接照着语法树把答案算出来。

**为什么要写这个看起来"重复"的东西**
它是编译器的**对照组**。同一段程序，一边编译成汇编丢进官方模拟器跑，
一边用它直接算，两边结果必须一模一样。不一致就说明编译器有 bug。

它不参与提交路径，只在自测时使用。

## 卡片 6 · `tools/fuzz_l3.py` —— 随机对拍测试

**干什么**
自己给自己出考题：随机生成几万道符合文法的程序，每道题穷举所有测量值组合，
逐一比对编译产物的执行结果和参考答案。

**为什么需要它**
赛题写明 L3 是"随机生成用例 + 穷举注入所有测量值组合 + 完全确定性判分"。
公开自测只给了**一道**题，过了不说明任何问题。所以我们自己搭一个同样的考场，
先把自己考到全对。

**参考答案从哪来（这是关键）**
每道随机题目会被同时写成**两种文本**：

```text
Hybrid-QASM 版本  ->  我们的编译器  ->  汇编  ->  官方模拟器  ->  结果 A
等价的 Python 版本 ->  CPython 直接执行                      ->  结果 B
```

A 和 B 必须完全一致。

用 Python 当参考答案，是因为这个迷你文法的写法（赋值、`if/else`、`+ - == !=`、
括号、优先级、左结合）**和 Python 恰好完全一致**，而 CPython 显然不会跟我们
犯同一个错误。这是一个真正独立的对照组——连"我们的语法分析器把结构读错了"
这类 bug 都能抓出来。（如果拿自己的解释器当参考，解析层的 bug 两边都会犯，就测不出来。）

**这个考官本身可信吗**
用**变异测试**验证过：故意往编译器里植入四种真实会犯的错，看它抓不抓得到。

| 植入的错误 | 结果 |
|---|---|
| 表达式改成右结合（`1 - 2 + 3` 会算成 `-4`） | 第 2 道题就抓到 |
| 临时寄存器从 `x10` 开始，踩掉测量位 | 第 2 道题就抓到 |
| 算完不清理临时寄存器 | 第 2 道题就抓到 |
| 分支跳转方向写反（`beq`/`bne` 互换） | 第 2 道题就抓到 |

**怎么跑**

```bash
python3 starter_kit/tools/fuzz_l3.py                 # 默认 2000 道
python3 starter_kit/tools/fuzz_l3.py --cases 20000   # 加大强度
python3 starter_kit/tools/fuzz_l3.py --seed 7        # 复现某一次
```

当前状态：4 个种子 × 5000 道 + 主种子 20000 道，累计约 30 万次测量值注入，**全部通过**。
另有 7 道固定回归用例每次都跑，防止改代码时把已经修好的坑又踩回去。
