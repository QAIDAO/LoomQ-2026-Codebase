# L3 零基础前传 · 为什么非得这么做

> 姊妹篇 [`L3-人话卡片.md`](L3-人话卡片.md) 回答的是「**每一步在干什么**」。
> 这一篇回答的是「**为什么非得有这一步**」——那些学过代码的人默认知道、
> 因而所有技术文档都会省略的东西。
>
> 读完这篇再回去读卡片，卡片里每一个看起来随意的决定都会变成"只能这样"。

---

## 起点：处理器不认识文字

我们写的这行东西：

```text
if (c[0] == 1) { r1 = 100; } else { r1 = 10; }
```

对人来说一目了然。但处理器**读不懂它**——不是"读起来吃力"，是**完全读不到**。
处理器不处理文字，它只做一件事：**从一张固定的清单里，按顺序执行一个个动作。**

所以整个 L3 就是在解决一件事：**把人写的一句话，拆成清单上的动作序列。**

这也是"编译器"这个词的全部含义。它听起来高深，实际上就是**一个翻译**——
只不过要翻译成的那门语言，词汇量小得可怜。有多小，往下看。

---

## 一、清单上只有 7 个动作

官方给的这台处理器，一共只认识 7 个动作：

| 动作 | 意思 |
|---|---|
| `li` | 把一个数字放进某个位置 |
| `add` | 把两个位置的数字相加，结果放进第三个位置 |
| `sub` | 同上，改成相减 |
| `addi` | 把某个位置的数字加一个固定的数 |
| `beq` | 如果两个位置的数字**相等**，就跳到某一行 |
| `bne` | 如果两个位置的数字**不等**，就跳到某一行 |
| `j` | 无条件跳到某一行 |

没了。**没有乘法，没有除法，没有 if，没有变量名，没有括号。**

我们要用这 7 个动作，拼出「if/else 嵌套、任意层、带加减法、带比较」的完整语义。
后面所有看起来别扭的设计，源头都是"只有这 7 个"。

---

## 二、「寄存器」= 处理器的手，一共 32 只

上面反复说的"某个位置"，学名叫**寄存器**。可以就理解成**处理器的手**。

这台处理器有 **32 只手**，编号 `x0` 到 `x31`。关于手，有三条铁律：

1. **手里只能攥一个数字。** 一只手一个数，换一个数就把原来的挤掉。
2. **只有攥在手里的数才能参与运算。** 处理器不能"拿一个手里的数跟凭空的 5 相加"——
   要跟 5 相加，得先有一只手攥着 5。
3. **`x0` 这只手被焊死了，永远是 0。** 写它无效，读它总是 0。
   （听起来没用，其实非常有用：需要一个 0 的时候不必浪费一只手去攥。）

**这三条铁律，直接解释了你在卡片里看到的三件事：**

**① 为什么 `r1..r9` 要"映射"到 `x1..x9`**
因为程序里的变量 `r1`，在处理器那边根本不存在——它只是我们**指定用第 1 只手来代表 r1**
的一个约定。赛题把这个约定定死了：`r1` 用 `x1`，`r2` 用 `x2`，依此类推。
"映射"这个词唬人，实际就是"哪只手代表谁"的分工表。

**② 为什么 `if (c[0] == 1)` 必须先把 1 装进一只手**
因为铁律 2。`beq`/`bne` 只会比较**两只手**，不会比较"一只手和一个数字"。
所以 `c[0] == 1` 不能直接翻译，得先 `li x20, 1`（让第 20 只手攥住 1），
再 `bne x10, x20, ...`（比较第 10 只手和第 20 只手）。

这不是我们想多绕一步，是清单上**根本没有"手跟数字比"这个动作**。

**③ 为什么需要"临时寄存器"，为什么它们必须避开 x10**
算 `r1 + 5 - r2` 时，`r1 + 5` 的中间结果得先放在**某只手**里，才能接着减 `r2`。
这只手就是"临时寄存器"——它不代表任何变量，只是个中转。

而 `x10` 起的那些手**被赛题征用了**：量子测量的结果 `c[0]`、`c[1]` 会由评测系统
直接塞进 `x10`、`x11`。我们的中间结果如果放进 `x10`，就把人家塞进来的测量结果**挤掉了**
（铁律 1：一只手只能攥一个数）。所以我们的临时用手从 `x20` 起，并且会随测量位数量继续往后让。

**④ 为什么算完还要"清零"临时寄存器**
官方模拟器最后会把**所有手里非零的数**都报出来当作运行结果。
临时用过的手里如果还攥着中转的数，就会混进最终答案里。所以用完得摊开手。

## 三、处理器没有 if，只有「跳到第几行」

清单上没有 `if`。只有 `beq` / `bne` / `j` 这三个"跳到第几行"。

所以 `if/else` 必须用"跳"重新搭出来。而搭法有个反直觉的地方：

```text
if (条件) { A } else { B }
```

翻译出来是：

```asm
    <算出条件两边的值>
    如果条件"不成立"就跳到 L_ELSE     ← 注意是不成立
    A 的动作
    j L_END                          ← A 做完必须主动跳过 B
L_ELSE:
    B 的动作
L_END:
```

**两个关键点：**

1. **分支判断的是条件的反面。**
   人的写法是"条件成立就做 A"，但指令的写法是"条件不成立就**绕开** A"。
   因为指令默认是一行接一行往下走的，A 就摆在下一行——条件成立时什么都不用做，
   自然就走进 A 了。要处理的反而是"条件不成立时怎么别走进去"。
   所以卡片里写「`==` 用 `bne` 跳走」，不是笔误。

2. **A 做完必须主动跳过 B。**
   处理器不知道 A 和 B 是"二选一"的关系。它只会一行一行往下执行，
   做完 A 会径直撞进 B 里去。所以必须在 A 末尾放一个 `j L_END` 把它推开。

**`L_ELSE:` 和 `L_END:` 是什么** —— 就是给某一行起个名字（叫"标签"），
好让 `j`、`beq` 知道要跳到哪儿。因为"跳到第 47 行"这种写法一旦前面增删一行就全错了，
起名字就不会错。名字后面带编号（`L_ELSE_1`、`L_ELSE_2`）是因为一个程序里会有很多个 if，
每个都得有自己的独一份名字，不能重名。

## 四、为什么要拆成四步，而不是一步到位

看上去可以简单粗暴：直接扫这段文字，看到 `if` 就吐一条跳转，看到 `=` 就吐一条赋值。

行不通。因为这段路上其实混着**三种完全不同的问题**：

| 问题 | 例子 | 归谁管 |
|---|---|---|
| **排版问题**：哪些字符算一个词？ | 空格换行怎么算？`==` 是一个词还是两个？注释要不要？ | 分词 |
| **结构问题**：谁从属于谁？ | `if` 里面套的那个 `if`，它的 `else` 到底配给谁？`a + b - c` 谁先算？ | 语法分析 |
| **硬件问题**：用哪几条指令实现？ | 常数要不要先装进手里？临时用哪只手？ | 代码生成 |

**如果不拆，每写一个函数都要同时想这三件事。**更要命的是排查问题：
程序算错了，你不知道是"词切错了"、"结构理解错了"还是"指令选错了"——
它们会互相伪装成对方的样子。

拆开之后，每一步只回答一类问题，**每一步的输出都能单独拿出来看**：
分词错了看得见词，结构错了看得见树，指令错了看得见汇编。
这就是为什么调试和答辩时能一层一层讲清楚。

（第四步 `hybrid.py` 的拆分是个更早的问题：先得把量子部分和经典部分分开，
因为它们要交给**两种不同的硬件**。）

## 五、为什么中间要变成一棵「树」

因为**文字是平的，意思是有层次的**。

```text
r1 = r1 + 5;
```

这行字从左到右是平铺的六个词。但它的意思有主次：整件事是"赋值"，
赋的值是"一次加法"，加法的两边分别是"r1"和"5"。画出来是这样：

```text
        赋值给 r1
            │
          加法
         ╱    ╲
       r1      5
```

**为什么非要画出来** —— 因为有层次的关系，平铺的文字表达不了。最典型的是这两个：

- `a + b - c` 到底是 `(a+b)-c` 还是 `a+(b-c)`？两者答案不同（试试 `1-2+3`：
  一个是 2，一个是 -4）。文字里看不出来，树里一目了然。
- `if` 套 `if` 时，那个 `else` 配给里面还是外面？同样只有树能说清。

树一旦建好，后面两件事就都变成了**在树上走一遍**：
往下走一遍生成汇编（第三步），往下走一遍直接算出答案（参考解释器）。
同一棵树，两种走法，这也是为什么那两个模块能互相当对照组。

## 六、回头看那四个"坑"

现在再看卡片里提到的那四个坑，它们一个都不是巧合，全是上面这些铁律的直接后果：

| 坑 | 它其实是哪条铁律 |
|---|---|
| 常数必须先装进寄存器才能比较 | 二·铁律 2：只有攥在手里的数才能参与运算 |
| 临时寄存器不能用 x10 起 | 二·铁律 1：一只手只能攥一个数，会把测量结果挤掉 |
| 临时寄存器用完要清零 | 模拟器把"所有非零的手"当作最终结果上报 |
| `==` 要用 `bne` 跳 | 三：分支表达的是"什么时候绕开"，不是"什么时候执行" |

**这四个坑我们都踩过，也都用随机测试抓回来了**——具体怎么抓的，见卡片 6。

## 尾注：这篇文档为什么会存在

正常的技术项目不会写这一篇。因为写代码的人默认彼此都知道"寄存器是什么"、
"处理器一行行往下走"，写出来反而显得啰嗦。

但这个比赛的题眼是**"不奖励最懂量子的人，奖励让最多人能用上量子的人"**。
省略掉的这一层，恰恰是把人挡在门外的那层——
它不难，只是**从来没有人愿意为门外的人写一遍**。

所以这一篇不是附录，是这个项目主张的一部分。
