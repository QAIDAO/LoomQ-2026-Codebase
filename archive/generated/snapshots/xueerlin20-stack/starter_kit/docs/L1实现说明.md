# L1 实现说明

## 我们要解决什么

L1 的目标，是接收一份 OpenQASM 2.0 电路，把它转换成 SpinQ、Amazon Braket 和 OriginQ 能执行的格式，然后把三家平台的运行结果整理成比赛规定的统一结构。

这件事表面上像是“换一种 QASM 写法”，实际包含三步：

1. 解析输入电路，弄清楚寄存器、量子门和测量关系。
2. 根据目标平台生成对应的 QASM 2、QASM 3 或 OriginIR。
3. 执行电路，并把各 SDK 不同格式的结果统一成比赛要求的 counts。

项目里这三步分别放在：

- `qasm_L1/parser.py`：解析输入；
- `qasm_L1/emitter.py`：生成目标平台代码；
- `qasm_L1/runners.py`：调用 SDK 并整理结果。

这样拆分的好处是，转换代码只负责电路语义，runner 只负责平台差异。以后增加平台或排查结果问题时，不需要把整个流程混在一起修改。

## 为什么结果位序容易出错

量子电路里有两种不同的比特：

- `q[i]` 是量子比特，参与量子门运算；
- `c[i]` 是经典比特，用来保存测量得到的普通 0 或 1。

测量语句决定量子测量结果写到哪个经典位置。例如：

```qasm
measure q[0] -> c[1];
measure q[1] -> c[0];
```

这不是普通的一一对应测量，而是把两个结果交叉存放。

假设某次测量得到：

```text
q[0] = 0
q[1] = 1
```

写入经典寄存器后就是：

```text
c[1] = 0
c[0] = 1
```

比赛规定 counts 的 key 必须写成：

```text
c[n-1]…c[1]c[0]
```

所以这个例子的正确 key 是 `01`。

### 不能只把字符串反转

SpinQ、Braket 和 OriginQ 对原始测量结果的排列方式并不完全一致。SpinQ 和 Braket 的结果更接近量子位测量顺序，Braket 还会通过 `measured_qubits` 告诉我们每个结果位置对应哪个量子位；OriginQ 则会直接体现经典位映射。

最初的处理方式是对 SpinQ 和 Braket 的结果执行一次字符串反转：

```python
key[::-1]
```

当电路使用：

```qasm
measure q -> c;
```

时，量子位和经典位刚好一一对应，整体反转通常能得到正确结果。但遇到交叉测量，它就不够用了，因为交叉映射是任意位置重排，不一定等于首尾反转。

Bell 和 GHZ 电路也很难发现这个问题，因为它们主要产生 `00`、`11`、`000`、`111`。这些字符串正着看和反着看完全一样，即使位序处理错了，测试结果仍可能通过。

### 当前的归一化方法

现在不再把 SDK key 简单理解成经典寄存器字符串，而是按下面的顺序处理：

1. 确定原始 key 的每个字符属于哪个 `q[i]`；
2. 读取目标 QASM 中所有 `q[i] -> c[j]` 测量关系；
3. 把每个量子测量值写到对应的经典比特；
4. 最后固定按 `c[n-1]…c[0]` 拼出比赛要求的 key；
5. 如果多个原始 key 整理后变成同一个经典 key，就合并它们的计数。

这个处理支持：

- 普通整寄存器测量；
- 逐位测量；
- 任意交叉映射；
- 多个量子寄存器和经典寄存器；
- Braket 的自定义 `measured_qubits` 顺序。

OriginQ 已经按经典寄存器语义返回结果，因此保持原来的规范化方式，避免重复重排。
