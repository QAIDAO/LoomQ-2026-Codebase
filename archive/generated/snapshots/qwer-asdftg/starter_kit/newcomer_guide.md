# LoomQ 零基础五分钟路线

这条路线适合会打开终端、但从没装过量子 SDK 的 Python 学习者、实验人员和跨学科
开发者。目标是先看懂一次小实验的输入和结果；它不承诺真实设备、也不需要 API Key。

## 第 0 分钟：先拿到一张路线图

在仓库根目录运行：

```bash
python -m starter_kit.l2_cli --guide
```

这条命令完全离线。它不会调用 LLM，不会消耗 Key，也不会把任务交给真实量子设备。

## 第 1 分钟：认识五个词

| 词 | 把它想成 | 现在能做什么 |
| --- | --- | --- |
| QASM | 写给量子线路看的食谱 | 打开 `starter_kit/circuits/bell.qasm`，看 `h` 和 `cx` 两个步骤。 |
| 后端 | 执行食谱的厨房编号 | L1 可把同一份 QASM 转给不同平台的运行器。 |
| 模拟器 | 练习厨房 / 试做台 | 先在电脑中重复“试做”，快、可复现，也没有真机排队。 |
| shots | 把同一食谱重复做的次数 | 次数越多，看到的比例通常越稳定。 |
| 真机 QPU | 真实厨房 | 可能有噪声、费用和排队；只有平台明确返回任务记录后，才能说真的运行过。 |

## 第 2–3 分钟：读一个最小 Bell 实验

Bell 线路只有两步：先让第一个量子位出现两种可能，再让第二个量子位和它建立关联。
每一次测量会得到一条位串，例如 `00` 或 `11`。这不是“每次都得到同一个答案”，而是
多次重复后常常看到两个位同为 0 或同为 1。

如果已经有 counts（位串到出现次数的 JSON），运行：

```bash
python -m starter_kit.l2_cli --explain-counts '{"00":4102,"11":4090}'
```

输出中的 `#` 柱子只表示这批样本的频率。`00` 和 `11` 同时出现、且占主导时，说明
这批读数呈现“两个位相同”的关联；它本身不能证明硬件质量、不能证明纠缠质量，也不能
说明结果一定来自真机。

## 第 4 分钟：先在模拟器复现

从 `starter_kit/` 构建一次固定依赖的 Docker 环境：

```bash
cd starter_kit
docker build -t loomq-l1 .
docker run --rm -w /workspace loomq-l1 python -m starter_kit.evaluator --level l1 --target spinq,originq,braket --shots 8192
```

这一步先检查试做后的常见结果，是否符合食谱预期；它是模拟器/本地运行器的公开检查，
不是 QPU 任务。看到通过后，你已经完成了“读线路、运行、看 counts”的第一圈练习。

## 第 5 分钟：选择下一步

这一分钟决定下一次在哪里做实验：先继续用模拟器，因为它快、免费、可重复；只有需要
确认真实设备表现时，才需要考虑真机。

- 想改线路：从 `bell.qasm` 复制一份，先在本地 evaluator 中检查。
- 想用自然语言描述线路：仅在评测环境或你自己已配置
  `LOOMQ_LLM_BASE_URL`、`LOOMQ_LLM_API_KEY`、`LOOMQ_LLM_MODEL` 后，运行
  `python -m starter_kit.l2_cli "生成一个 3 比特 GHZ 态并进行全测量"`。
- 想使用真机：先确认平台账号、费用、排队和设备权限；提交后保留平台返回的 job ID、
  shots、时间和原始结果。没有这些记录时，不把结果写成“真机成功”。

遇到错误时，先看 CLI 的简短错误类别：缺什么环境变量、连接是否超时、是否被限流，或
QASM/后端选择哪里不符合约束。错误信息不会显示 API Key 或模型原文；修正一项后再试。
